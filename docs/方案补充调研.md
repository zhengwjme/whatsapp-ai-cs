# 第二批调研：还有哪些方案（2026-09-17 取数）

> 前情：约束是**个人号 + 低版本 Windows（无 WSL/Docker）+ 尽量少三方 + 中文客服**。
> 上一批覆盖了 WAHA / Evolution / n8n / Chatwoot / Typebot / Dify / MaxKB / AnythingLLM / WeKnora / RAGFlow。
> 这份只写**新发现**和**已排除**，不重复。

## 0. 速览

**三个新发现**：
1. **whatsmeow-node**（Node 版 whatsmeow，MIT，有 `win32-x64` 预编译）→ 可以把我们现有 bot 的传输层从 Baileys 换成 whatsmeow，**不用 Docker、不用 Go**，老 Windows 直接 npm 装。
2. **WuzAPI**（Go 单二进制 REST API，MIT，基于 whatsmeow，自带 webhook + 面板 + Swagger）→ **不需要 Docker 的 WAHA 替代品**，代价是要自己 `go build`（官方 release 没放二进制）。
3. **whatsmeow**（7.3k⭐，MPL-2.0）本身——多个跑生产的人反馈它比 Baileys 会话更稳、内存更低。

**两个直接排除**：LangBot（WhatsApp 官方状态还是 🚧 开发中）、chatgpt-on-wechat/CowAgent（没有 WhatsApp 通道，已迁到新组织）。

## 1. 新发现 A：whatsmeow-node —— 升级我们现有 bot 的最低成本

| 项 | 值 |
|---|---|
| npm | `@whatsmeow-node/whatsmeow-node` 0.7.0 |
| 许可 / 依赖 | **MIT**；可选依赖自带 `win32-x64`、`win32-arm64`、`darwin-*`、`linux-*`（含 musl）**预编译** |
| Node | `>=18` |
| 底座 | Go 的 [whatsmeow](https://github.com/tulir/whatsmeow)（7.3k⭐, MPL-2.0，Mautrix 团队维护，Matrix 桥接生态跑了好几年） |

**为什么值得考虑**（对比 Baileys）：
- 会话稳定性：Baileys 的 `auto-logout`／需要反复重新认证是老问题；whatsmeow 侧有生产用户反馈「换过去之后不再掉线、CPU 降幅很大」。⚠️ 这是**社区经验，不是基准测试**，不同人负载不同。
- 内存：官方迁移文档称 ~10–20MB vs Baileys ~50MB。
- 维护上游：Baileys 这库换过好几轮 fork（adiwajshing → WhiskeySockets → 其他），whatsmeow 上游单一稳定。

**代价**：
- 0.x 版本，生态新；接口与 Baileys 不同（`conversation` 而不是 `text`，事件名不同，见[迁移指南](https://nicastelo.github.io/whatsmeow-node/docs/guides/migrate-from-baileys)）。
- **必须重新扫码**（Baileys 的 auth state 不能迁移）。
- 换它 = 我们现有 `bot-baileys.mjs` 那 60 行传输层重写；`lib.mjs`（判定/去重/上下文/转人工）完全不动——这正是当初把传输层拆出来的原因。

## 2. 新发现 B：WuzAPI —— 不用 Docker 的 WAHA 替代

| 项 | 值 |
|---|---|
| 仓库 | [asternic/wuzapi](https://github.com/asternic/wuzapi) 1.0k⭐，MIT，Go |
| 形态 | 单二进制 REST 服务，多会话、多用户 |
| 自带 | Swagger（`/api`）、扫码页（`/login`）、**看板（`/dashboard`）**、webhook（POST + 可订阅事件）、S3 存储 |
| 运行 | `go build .` → 一个可执行文件；Windows 上直接跑（Go 支持），也可交叉编译 |
| 缺陷 | **官方 release（v1.0.8）没上传任何编译产物** → 要自己装 Go 工具链构建；上游 whatsmeow 有破坏性变更时它要跟着改 |

对比 WAHA：能力重叠（都是「个人号 → HTTP API + webhook」），差别是 **WuzAPI 不需要 Docker**，代价是要 Go 工具链 + 自己构建，生态和文档比 WAHA 小一个量级。

**要接我们的 bot** 需要写一个 ~30 行的适配（webhook 载荷字段不同 + 发消息端点不同），因为 `lib.mjs` 的 io 接口是抽象好的。

## 5. 建议动作（按性价比排序）

1. **什么都不换**：当前 `lib.mjs` + 两个传输层已经满足三条硬约束。先跑起来观察 2 周，看有没有掉线/重连问题。
2. **真的掉线频繁** → 加第三条传输 `whatsmeow-node`（同结构、win 预编译、MIT），我们这边大约 60 行 + 一次重新扫码。旧的两条保留做回退。
3. **哪天必须上 Docker 之外的 HTTP 网关**（比如想给多个号统一管）→ WuzAPI，但要先装 Go 构建，并接受它生态小。
4. **知识库** → 仍然按 `知识库选型.md` 上 MaxKB。
