# 个人 WhatsApp 号做 AI 客服 — 开源方案调研 + 最快落地

**一句话结论**：用 `WAHA`（单容器 WhatsApp HTTP API，Baileys 内核）+ 一个 150 行的 `bot.mjs` 接任意 LLM。个人号手机扫码即用，不需要 Meta 官方审核、不需要企业资质、不需要服务器（本机 Docker 就能跑）。

数据采集日：2026-09-17（GitHub API 实时取数）。

---

## 1. 最快路径（3 步）

```bash
cp .env.example .env      # 填 OPENAI_API_KEY（或 DeepSeek key）
docker compose up -d --build
open http://localhost:3000  # Swagger → POST /api/sessions {"name":"default"} → GET /api/screenshot 看二维码
```

手机 WhatsApp → 设置 → 已关联的设备 → 关联设备 → 扫上面的二维码。完事。之后任何人给你发消息，`bot.mjs` 自动回。

自检（改完逻辑先跑）：

```bash
node bot.mjs --selftest
```

**Windows 用户直接跳到 §8**，那条路径是单独写的。

## 2. 只有两种技术路线

| 路线 | 代表项目 | 资源/会话 | 抗协议变动 | 适用 |
|---|---|---|---|---|
| **协议直连**（复刻 WhatsApp 多设备 WebSocket 协议，无浏览器） | Baileys | ~50MB，秒起 | 弱（协议变了要等库跟进） | 多号、省资源、容器化 |
| **浏览器自动化**（无头 Chromium 跑 web.whatsapp.com） | whatsapp-web.js、Venom、WPPConnect | ~400–500MB，冷启数秒 | 强（跑的是 WhatsApp 自己的前端代码） | 单号、快速验证、要镜像官方客户端行为 |

单号自用 → 两者都行。**别自己从 Baileys 起手**：会话管理、重连、媒体、存储全得自己写，下面这些项目已经写完了。

## 4. 授权坑（真会咬人）

- **Baileys 的 libsignal 依赖是 GPLv3**。MIT 只是 Baileys 自身；静态链接后对外分发闭源产品会触发 copyleft 义务。自用/自托管无影响，**要卖盒子或 SaaS 才需要处理**（换 whatsapp-web.js 或走官方 API）。
- **Evolution API 是 Apache-2.0 + 两条例外**：不得删改其控制台 LOGO/版权；商用须在系统内显著告知「使用了 Evolution API」。违反即需商业授权。自用无所谓。
- **n8n 不是开源软件**，Sustainable Use License：可以内部用，不能拿它做转售的托管服务。
- Chatwoot/Dify/Flowise 都是「开源自托管 + 企业版」双轨，注意 `.ee` 目录别碰。

## 5. 封号风险（必须知道）

非官方库全部违反 WhatsApp ToS，**随时可能封号，无申诉**。降低概率：

- **别用主号**。买一张副卡/备用号，先跑 1–2 周。
- 别群发、别主动冷启动陌生人（这是封号第一原因；被动回复风险低得多）。
- 本方案的 `typingDelay()` 已在模拟「读—打字—发送」节奏；被限流就先调大。
- 营销触达/客户量真实到一定程度 → 换 **官方 WhatsApp Business Cloud API**（免费额度 + 按会话计费，不封号，但要企业资质、模板消息审核）。

## 6. 三个方案的取舍

| 方案 | 复杂度 | 代码量 | 什么时候选 |

## 8. Windows 部署（只在 Windows 上跑）

### 8.1 先装什么

| 选项 | 适合谁 | 成本 |
|---|---|---|
| **Docker Desktop（推荐）** | 个人 / 小公司（<250 人且年收入 <1000 万美元免费） | 装完即用，带 GUI、开机自启开关 |
| WSL2 里装 Docker Engine | 公司规模超了不想买许可 | 无 GUI，全命令行，多花 15 分钟 |

前置条件：Win10 2004+ 或 Win11（64 位）、BIOS 里虚拟化已开（VT-x / AMD-V）、给 Docker 至少 4GB 内存。

### 8.2 步骤（PowerShell，Win11）

```powershell
wsl --install                      # 装 WSL2 + Ubuntu，然后重启（Docker Desktop 依赖它）
# 装 Docker Desktop → Settings → General → 勾 "Start Docker Desktop when you sign in"
#                   → Settings → Resources → WSL Integration → 勾上 Ubuntu

cd C:\path\to\whatsapp1
Copy-Item .env.example .env        # 用记事本填 OPENAI_API_KEY
docker compose up -d --build
Start-Process http://localhost:3000
```

拿二维码（PowerShell 里 `curl` 是别名，要用 `curl.exe` 或 `Invoke-RestMethod`）：

```powershell
Invoke-RestMethod -Method Post http://localhost:3000/api/sessions -ContentType 'application/json' -Body '{"name":"default"}'
Invoke-RestMethod http://localhost:3000/api/screenshot -OutFile qr.png    # 打开 qr.png 用手机扫
Invoke-RestMethod http://localhost:8787/health                             # 应输出 ok
```

手机 WhatsApp → 设置 → 已关联的设备 → 关联设备 → 扫 `qr.png`。

### 8.3 为什么这套在 Windows 上不踩坑

- **没有 bind mount**：代码烘焙进镜像，SQLite 和登录态都在 Docker 命名卷里 → 不受 Windows 文件系统性能、CRLF 换行符、大小写不敏感的影响
- **端口只绑 127.0.0.1**：`3000` 和 `8787` 不对局域网开放，公共 Wi-Fi 下也不会弹 Defender 放行框，更不会被同事扫到你的 WhatsApp 面板
- **重启自愈**：compose 里 `restart: unless-stopped` + Docker Desktop 登录自启 = 关机重启后容器自动回来，登录态不丢
- **健康检查**：bot 容器自带 `HEALTHCHECK`，`docker compose ps` 能看到 `healthy`

### 8.4 Windows 专属坑

| 现象 | 原因 / 处理 |
|---|---|
| 合盖后不回消息 | Docker Desktop 跟随系统睡眠暂停。电源设置里插电时设「不睡眠」；唤醒后 WAHA 会自动重连，期间消息可能补发滞后 |
| 中文日志乱码 | PowerShell 5.1 默认不是 UTF-8：`chcp 65001`，或直接用 Windows Terminal + PowerShell 7 |
| `docker-compose` 找不到 | 用 v2 的 `docker compose`（空格），不要老版 `docker-compose` |
| `curl` 行为奇怪 | PS 里 `curl` 是 `Invoke-WebRequest` 的别名。用 `curl.exe`，或 `Invoke-RestMethod` |
| 内存吃紧 | Docker Desktop → Settings → Resources 调到 4–6GB；本次实测 WAHA(浏览器引擎) + bot 两容器常驻约 1.5–2GB |
| 换电脑 / 重装 | 备份两个卷即可：`docker run --rm -v whatsapp1_waha-sessions:/s -v "C:\backup":/b alpine tar czf /b/wa.tgz -C /s .`（bot 的 `bot-data` 同理） |

### 8.5 变体：bot 在 Windows 原生跑、只有 WAHA 在 Docker

想直接改 `bot.mjs` 不用重新 build 时可以这样（装 Node 24 即可，Node 24 自带 `node:sqlite`）：

```powershell
docker compose up -d waha          # 只起 WAHA
node bot.mjs                       # 原生跑 bot
```

此时容器访问不到 compose 网络里的 `bot` 服务名，要在 `.env` 里把 webhook 地址改成 Windows 主机：

```ini
WAHA_HOOK_URL=http://host.docker.internal:8787/webhook
```

改完 `docker compose up -d waha` 重启 WAHA 生效。**注意**：这个写法要求 bot 监听 `0.0.0.0`（默认就是），Defender 可能弹窗——只勾「专用网络」。

### 8.6 实测到什么程度

已在 Linux 容器里跑过：镜像构建成功、`/health` 返回 200、webhook 立即 200、重复消息 id 只触发一次回复（去重生效）、群消息被忽略、`node:sqlite` 在 alpine 上正常落盘（`/data/bot.db`）。**Windows 上的 Docker Desktop 与真实扫码收发这条链没实测**（本机是 macOS）。

## 9. 依赖清单：到底用了哪些三方服务

**一句话**：除了可选的知识库（MaxKB 等，也在你机器上自托管），运行时唯一的第三方服务是 **LLM API**——而这一个可以换成本地模型，换完就 100% 不出机器。

| 组件 | 谁提供 | 数据出你的机器吗 |
|---|---|---|
| WhatsApp 网络本身 | Meta 服务器 | **是**（消息必须经过它，这是 WhatsApp 的定义，绕不开） |
| WAHA | 自托管容器，Apache-2.0。**2026.6.1 起 Plus 功能全部并入 Core，完全免费无订阅** | 否。登录态在你本机的 Docker 卷里 |
| `bot.mjs` | 你的代码，150 行 | 否 |
| **LLM** | 默认 `.env` 指向 DeepSeek / OpenAI = **三方** | **默认是**：每条客户消息 + 上下文原文发到厂商 |
| 知识库（可选） | MaxKB / AnythingLLM / WeKnora 等，自托管 | 否——前提是它的 embedding 和 LLM 也指向本地 |
| Docker 镜像 | Docker Hub | 只在首次 `pull` 时需要网，之后离线能跑 |

### 9.1 改成 100% 本地（不出网）

Windows 上装原生 Ollama（自带 GPU 检测，不需 Docker/WSL）：

```powershell
# 从 ollama.com/download/windows 装 OllamaSetup.exe，然后
ollama pull qwen3:8b
ollama list
```

改 `.env` 三行：

```ini
OPENAI_BASE_URL=http://host.docker.internal:11434/v1   # bot 跑在容器里用这个
OPENAI_API_KEY=ollama                                   # 非空即可，Ollama 不校验
OPENAI_MODEL=qwen3:8b
```

bot 原生跑在 Windows 上时用 `http://localhost:11434/v1`。改完 `docker compose up -d bot` 重建容器生效。

**硬件门槛（Ollama 自己给的参考）**：6GB 显存可跑 7–8B Q4；无独显走 CPU，7B Q4 约几个 token/秒，做长回答会明显慢；3–4B 模型能应付纯 FAQ。

**务实建议**：本地小模型的客服话术质量明显不如云端大模型。混合最划算——常见 FAQ 走本地，涉及报价/交期的复杂对话走云端 API。

### 9.2 怎么验证「没有偷偷外联」

1. **看 WAHA 有哪些出站配置**：`http://localhost:3000/api/server/environment?all=false`（只返回 WAHA 自己的变量）
2. **断网实测**：拔掉网线/关 Wi-Fi 再发一条消息。如果本地模型这条链仍能回答，说明 bot 没有依赖任何云；反过来 WAHA 会立刻报连接错误——那就对了，它连的就是 WhatsApp
3. **抓一次连接**：Windows 上用「资源监视器 → 网络 → TCP 连接」看 `com.docker.backend` 的远端地址；除 WhatsApp 网段外应该只剩你配的 LLM 地址

**我没验证的**：WAHA 有没有隐藏的遥测上报。翻 `devlikeapro/waha-docs` 和 Core 的 `.env.example` 只看到 Prometheus 指标（要显式开 `WAHA_PROMETHEUS_TRACK_EVENTS`），没有发现遥测开关——但「没找到」不等于「不存在」，要确证跑上面第 3 步。

## 10. Windows 版本低、装不了 WSL/Docker 怎么办

### 10.1 先确认你属于哪种（PowerShell 一行）

```powershell
[Environment]::OSVersion.Version    # 看 Build 号
(Get-CimInstance Win32_OperatingSystem).Caption   # 看是家庭版还是专业版
```

| Build / 版本 | Docker Desktop | 走哪条 |
|---|---|---|
| Win10 19044+（21H2）/ Win11，家庭版也行 | ✅ 可装 | §8 |
| Win10 19041–19043 | ⚠️ WSL2 能开但 Docker Desktop 要 19044+ | §10.2 路线 A |
| Win10 ≤ 1909，或 21H2 以下的家庭版（无 Hyper-V） | ❌ 装不了 | §10.2 路线 A |
| Win7 / 8.1（Node 22 都装不上） | ❌ | §10.2 路线 B |

### 10.2 路线 A：完全不用 Docker（推荐）

不需要 WAHA —— 换成 **Baileys 直连**，就是 WAHA 内部用的同一个库。只要 Node ≥ 22.5（`node:sqlite` 从 22.5 起内置）。

```powershell
node -v                # 低于 v22.5 就去 nodejs.org 装 v24 LTS（Win10 1809+ 能装）
cd C:\whatsapp1
npm install            # 只有 baileys + qrcode-terminal 两个依赖，约 47MB
notepad .env           # 填 OPENAI_API_KEY；WHATSAPP_PHONE 填你的号（国家码开头，不带 +）
npm run login          # 终端出 8 位配对码
```

手机：WhatsApp → 设置 → 已关联的设备 → 关联设备 → **改用配对码登录** → 输入那 8 位。

**老 Windows 优先用配对码，别用二维码**：老控制台渲染二维码块字符容易糊成一团，配对码是纯文本。

验证连接成功：终端出现 `已连接 WhatsApp，开始自动回复`。

开机自启（不用 Docker）：

```powershell
schtasks /create /tn WhatsAppBot /tr "cmd /c cd /d C:\whatsapp1 && node --env-file-if-exists=.env bot-baileys.mjs" /sc onlogon /f
```

数据全在 `C:\whatsapp1\data\`（`bot.db` + `baileys-auth`），备份就是复制这个目录；换机器带上它就不用重新扫码。

### 10.3 路线 B：老到连 Node 22 都装不上（Win7 / 8.1）

装 VirtualBox **6.1**（6.1 才支持 Win7 宿主）+ Ubuntu Server 20.04 虚拟机，在虚拟机里原样跑 §8 那套 `docker compose up -d --build`。宿主机上什么都不用装 Docker。

- 虚拟机网络选**桥接网卡**（虚拟机直接拿局域网 IP，手机和电脑都好访问）；不想桥接就 NAT + 端口转发 3000/8787
- 老机器资源紧张也没关系：WAHA 默认就是 NOWEB 引擎（Baileys，不开浏览器），两个容器常驻约 1.5–2GB

### 10.4 两条传输的差别

| | WAHA（HTTP） | Baileys 直连 |
|---|---|---|
| 依赖 | Docker | 只要 Node + npm |
| 额外能力 | 面板、Swagger、多号、媒体、重连可视化 | 少一层，启动快，改代码不用 rebuild |
| 登录态位置 | Docker 卷 `waha-sessions` | `data/baileys-auth` |
| 入口文件 | `bot.mjs` | `bot-baileys.mjs` |

业务逻辑**完全共用** `lib.mjs`，所以换传输不用改判定、上下文、转人工这些逻辑。

### 10.5 实测到什么程度

- **Baileys 通道真跑过**：连上了 WhatsApp（`connected to WA`），二维码正常出图，配对码路径返回真实 8 位码；加静音 logger 后终端只剩我们自己那 4 行输出
- **WAHA 通道重构后复测**：容器 health 200、webhook 立即 200、同一消息 id 只触发一次回复、`docker inspect` 健康状态 `healthy`
- **没测**：低版本 Windows 本机、虚拟化环境、真实扫码后的收发（我这台是 macOS）

## 11. bot 到底在干什么 / 能不能换成现成的

### 11.1 那 150 行只干六件事

| # | 职责 | 缺了会怎样 |
|---|---|---|
| 1 | 收事件（WAHA webhook / Baileys 事件） | 没有入口，模型永远不知道有新消息 |
| 2 | 过滤（自己发的、群聊、状态广播、空消息） | 机器人跟自己的回复互相触发，死循环 |
| 3 | **幂等去重**（按消息 id 落库） | 传输层重试 = 同一条消息回两遍（WAHA 文档明确会重试） |
| 4 | 上下文（每个客户最近 12 轮，SQLite 持久化） | 每个问题都是新对话，客户得反复自我介绍 |
| 5 | 调模型（OpenAI 兼容，可指向本地 Ollama / 自建 MaxKB） | 没大脑 |
| 6 | 回发的产品化细节：打字状态、拟人延迟、转人工关键词暂停、失败不崩、`/health` | 秒回像机器人 → 容易被风控；客户喊「人工」没人接 |

第 3、6 项是**产品细节，不是技术难点**——现成方案也躲不掉，只是换成图形界面里点。

### 11.2 现成替代品对比

| 方案 | 替代了哪几格 | 缺口 | 低版本 Windows（无 Docker） |
|---|---|---|---|
| **n8n + 官方节点** | 1–5 全替代，可视化画 | 不是 OSI 开源（Sustainable Use License）；多一个常驻进程；3 和 6 仍要自己画 | ✅ `npm install -g n8n` 原生跑，官方有 [WAHA 节点](https://github.com/devlikeapro/n8n-nodes-waha) + [模板仓库](https://github.com/devlikeapro/waha-n8n-templates) |
| **Evolution API 内置 bot** | 1–5 全替代，**零代码** | 必须 Docker + Postgres + Redis；3 和 6 的细粒度不如自己写 | ❌ |
| **Typebot**（10.3k⭐） | 可视化对话流 | 只对接 Evolution，不对接 WAHA；同样要 Docker | ❌ |
| **Chatwoot**（36.9k⭐） | 人工坐席 + AI 回答 + 工单 | 重（Rails+PG+Redis）；WhatsApp 接的是 Evolution／官方 API | ❌ |
| **Dify / MaxKB** | 只替代第 5 格（模型+知识库） | **不替代 bot**，仍要有人接 WhatsApp 事件 | ✅ 但省不掉 bot 或 n8n |
| 现成「WhatsApp AI bot」仓库<br>（GhostReply、wingman、GX framework） | 全替代 | 0–1 颗星、单作者、无审计；拿客服主链路赌它不划算 | 不推荐 |

### 11.3 建议

- **自己这台机器、单号、要跑得久** → 保留这 150 行。没有任何现成项目同时满足「低版本 Windows + 无 Docker + 零额外进程」这三条。
- **想零代码、以后还要串表格/CRM** → 上 n8n，用官方 WAHA 节点；在低版本 Windows 上它是唯一装得上的可视化方案（Node 原生装，不吃 Docker）。
- **要人工坐席/工单/多渠道** → Chatwoot，但那条路必须 Linux/Docker，老 Windows 只能走 §10.3 的虚拟机。
- **只缺知识库** → 加 MaxKB（见 `知识库选型.md`），bot 继续当胶水。模型和知识库随时可换，换传输也不用改逻辑（都在 `lib.mjs`）。

维护责任划分：**协议层**（WhatsApp 改协议会不会挂）由 Baileys/WAHA 承担；**业务层**（判定、去重、转人工、上下文）由这 150 行承担——这两件事本来就不该由同一个项目干。
