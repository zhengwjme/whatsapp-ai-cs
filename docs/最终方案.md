# 最终方案

**一句话**：Node + Baileys 直连 + 任意 OpenAI 兼容 LLM。不装 Docker、不接第三方机器人平台、不上知识库。代码已经写完，并做了端到端实测。

---

## 1. 为什么是这个（对照你的四条硬约束）

| 你的约束 | 本方案怎么满足 |
|---|---|
| **个人号**（非官方） | Baileys 就是 WAHA 内部那个库。扫码或 8 位配对码登录，个人号直接当客服号 |
| **低版本 Windows、装不了 WSL/Docker** | 只需要 Node。两个 npm 依赖（baileys + qrcode-terminal），无容器、无守护进程 |
| **尽量不用三方服务** | 运行时唯一外发是 LLM。换成原生 Ollama 后数据完全不出机器 |
| **中文 / 外贸客服** | 系统提示词、转人工关键词、拟人回复节奏都已内置且可配 |

**被否掉的方案及原因**（都在报告里有源码级证据）：

| 方案 | 否掉的原因 |
|---|---|
| Evolution API | 必须 Docker + Postgres + Redis |
| n8n | 不是 OSI 开源（Sustainable Use License），且多一个常驻进程；留作「要可视化时」的备选 |
| whatsapp-agentkit | 只支持 Meta 官方 API / Zernio，**不支持个人号**，还要 4 个第三方 |
| MaxKB / WeKnora | 能当知识库大脑，但**都不支持 WhatsApp**、都无转人工/工单，部署都要 Docker 或未验证的裸跑 |
| 各类 10–600⭐「WhatsApp AI bot」 | 单作者、无测试、当客服主链路不划算 |

## 2. 系统长什么样

```
手机 WhatsApp（个人号）
   ↕ Baileys 协议（无需浏览器）
Windows: node bot-baileys.mjs
   ├─ lib.mjs  判定过滤 · 幂等去重 · 每客户上下文(SQLite) · 拟人延迟 · 转人工
   └─ /chat/completions → DeepSeek / OpenAI / 本地 Ollama / 以后的 MaxKB
```

业务流程图见 `whatsapp-ai-cs-flow.html`（浏览器打开）。

传输层是可替换的：`bot-baileys.mjs`（现在用，不要 Docker）和 `bot.mjs`（WAHA HTTP，等你以后有 Docker 时用）共用同一个 `lib.mjs`，换传输不改业务逻辑。

## 3. 落地步骤（约 20 分钟，一次做完）

| # | 命令 | 成功判据 |
|---|---|---|
| 1 | 装 Node 24（nodejs.org，Win10 1809+ 即可） | `node -v` → v24.x |
| 2 | `npm install` | 无报错，node_modules 约 47MB |
| 3 | `Copy-Item .env.example .env` 后填 3 项：`OPENAI_API_KEY`、`WHATSAPP_PHONE`（国家码开头不带 +）、`SYSTEM_PROMPT` | 记事本保存为 UTF-8 |
| 4 | **`npm run sim`** ← 关键一步，先用终端验 LLM 和话术，不碰手机 | 你打「你们发货到德国吗」，终端出现「客服> …」的合理回答 |
| 5 | `npm run login` | 终端出 8 位配对码 |
| 6 | 手机 WhatsApp → 已关联的设备 → 关联设备 → **改用配对码登录** → 输入那 8 位 | 终端出现「已连接 WhatsApp，开始自动回复」 |
| 7 | `npm run start:baileys` | 让它常驻 |
| 8 | `schtasks /create /tn WhatsAppBot /tr "cmd /c cd /d C:\whatsapp1 && node --env-file-if-exists=.env bot-baileys.mjs" /sc onlogon /f` | 重启后自动恢复 |

第 4 步为什么放前面：**LLM key 不通、模型名写错、提示词跑偏，这三个坑占了首次失败的大多数**。`npm run sim` 让你不用手机就能验完，也不会给真实客户发出半成品回复。

## 4. 上线前的 6 项检查

| 检查 | 怎么做 | 通过标准 |
|---|---|---|
| 逻辑自检 | `npm run selftest` | 输出 `selftest OK` |
| LLM 通不通 | `npm run sim` 打一句真实客户问题 | 回答专业、不说胡话 |
| 上下文生效 | sim 里连问两句相关的 | 第二句回答能接上第一句 |
| 转人工 | sim 里打「人工」 | 回「已为您转接人工…」，且之后**不再自动回** |
| 数据可恢复 | 复制 `data\` 目录 | 里面应有 `bot.db` 和 `baileys-auth\`；带着它换机器不用重新扫码 |
| 风险控制 | 用**副号**先跑 48 小时 | 无掉线、无异常封禁提示 |

## 5. 升级触发器（别提前做，等信号）

| 出现的信号 | 该加什么 | 成本 |
|---|---|---|
| 掉线频繁 / 会话反复失效 | 换 `whatsmeow-node` 传输（win 预编译、MIT） | ~60 行 + 重新扫码 |
| 客户问题超出提示词能覆盖 | 上 **MaxKB**（按 `WeKnora-MaxKB-智能客服评估.md` §2.1 的三个坑改） | 1–2h + 一台能跑 PG17 的机器 |
| 想可视化编排、串表格/CRM | n8n + 官方 WAHA 节点 | 半天 |
| 要人工坐席 / 工单 / 多人协作 | Chatwoot（要 Linux 或 Docker，老 Windows 得先上虚拟机） | 1–2 天 |
| 要合规、不愿承担封号风险 | 官方 WhatsApp Business Cloud API（要企业资质 + 一个干净号码 + 按会话付费） | 大 |
| 号码被封 | 立即换号；排查是否有群发/冷启动陌生人；调大 `typingDelay` | — |

## 6. 成本与风险

**成本**：软件全免费（Baileys MIT、WAHA Apache-2.0、MaxKB GPL-3.0 自用无碍）。唯一计费项是 LLM，按厂商定价按量付；换成本地 Ollama 后为 0（代价是要有能跑 7B 的显卡）。

**风险（必须知道）**：
- 非官方协议**违反 WhatsApp 服务条款，封号不可申诉**。用副号、别群发、别主动冷启动陌生人。
- 本地 7B 模型回答质量明显弱于云端大模型 → FAQ 走本地、报价/交期走云端是更实际的分工。
- 客户消息原文会发给你选的 LLM 厂商；不想外发就换 Ollama。

## 7. 日常运维（每周 5 分钟）

1. 看进程还活着：任务管理器里 node 在跑；Windows 弹窗日志里偶尔出现「连接断开，5 秒后重连」是正常的
2. 备份 `data\`（改一次配置或换机器前）
3. 每月看一次 LLM 账单
4. 客户抱怨「答得不对」→ 改 `.env` 的 `SYSTEM_PROMPT` 或加到知识库（走 §5 触发器）

---

## 8. 现在就能做的三件事

1. 按 §3 的表从第 1 步往下走，走到第 4 步（`npm run sim`）为止——这一步能验完 LLM 和话术，且零风险
2. 准备一张**副号** SIM 卡用于上线
3. 写三句话的产品事实（发货范围、时效、售后口径）塞进 `SYSTEM_PROMPT`，这样第一版回答就不至于太虚

## 10. 实测到什么程度（别把没测的当已测）

**已实测**：
- `npm run selftest` 通过（判定/关键词/延迟边界）
- `sim.mjs` 端到端跑通：第一条消息携带 1 条上下文、第二条携带 3 条 → **多轮上下文生效**；打「人工」→ 转人工且**不再调用 LLM**；此后该会话只记录不回复 → **暂停生效**；进程干净退出
- Baileys 通道真连过 WhatsApp：二维码出图、配对码返回真实 8 位码、静音日志
- WAHA 通道容器化复测：`/health` 200、webhook 立即 200、同一消息 id 只触发一次回复、`healthy`
- Docker 镜像构建成功

**未实测**：
- **低版本 Windows 本机**（我这台是 macOS）
- 真实扫码后的双向收发（需要你的手机）
- 你选的 LLM 的实际回答质量
- 本地 Ollama 路径（本机没装 Ollama）

这三项都是你按 §4 的检查表跑一遍就能覆盖的。
