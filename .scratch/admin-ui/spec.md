# Spec: 管理界面

Status: ready-for-agent

术语以根目录 `CONTEXT.md` 为准（客户、运营、管理员、机器人、会话、会话历史、转人工、运营接管、手动转人工、转人工话术、转人工期、恢复接待）。架构取舍见 ADR 0002（管理界面跑在机器人进程内，只允许本机访问、不鉴权；`.env` 是唯一配置来源）。

## Problem Statement

管理员是英国的非技术人员，只有一台 Windows 电脑，通常同时也是运营。现在所有操作都要在终端里完成：

- 登录 WhatsApp 要扫终端里用字符拼成的二维码，或从终端日志里找配对码。账号被登出后，要自己去数据目录删登录态文件再重新登录。
- 改机器人的话术、转人工关键词、转人工期时长或模型设置，要用记事本编辑 `.env`。保存时得记得选 UTF-8 编码，改完还要重启。改错了也没有提示。
- 看不到哪些会话正处于转人工期、还剩多久，也看不到机器人对每位客户说过什么。
- 机器人接待得不对时，没法立刻让它闭嘴，只能自己去回复一条（触发运营接管）；想让机器人提前恢复接待，只能干等转人工期到期。
- 在电脑前办公时，要回复客户还得拿起手机。

## Solution

`npm start` 时，机器人在同一进程里启动一个只允许本机访问的管理界面，并自动在浏览器中打开。界面默认英文，可切换中文，分四块：

1. **连接**：显示 WhatsApp 连接状态（已连接、断线重连中、已登出）。需要登录时直接在页面上显示二维码，也可以填号码获取配对码。提供"退出并重新关联"按钮，点击时二次确认。
2. **配置**：用表单修改机器人的话术、行为和模型连接配置。保存后写回 `.env`，立即生效，不用重启。
3. **会话**：会话列表显示电话号、客户的 WhatsApp 昵称、是否在转人工期及剩余时长，按最后一条消息的时间排序。点开可以看只读的会话历史，客户、机器人、运营三方分别标出。
4. **干预与回复**：对某个会话可以手动转人工（机器人静默，客户察觉不到），或恢复接待（机器人重新接待，不给客户发任何消息）。也可以在界面里直接给客户发文字消息，效果等同于运营在手机上回复，即运营接管。

界面每 3 秒轮询一次刷新。终端里的二维码和日志照常保留，浏览器打不开时还能兜底。

## User Stories

1. 作为管理员，我希望 `npm start` 后浏览器自动打开管理界面，从而不用记网址。
2. 作为管理员，我希望管理界面的地址在终端里也打印出来，从而在浏览器没有自动打开时能手动访问。
3. 作为管理员，我希望管理界面只能在本机打开，从而不用担心同一网络里的其他人看到客户对话、改掉机器人配置。
4. 作为管理员，我希望能通过 `.env` 修改管理界面的端口，从而在默认端口被占用时换一个。
5. 作为管理员，我希望管理界面启动失败（例如端口被占用）时机器人照常工作，终端里给出清楚的提示，从而管理界面的问题不会影响对客户的回复。
6. 作为管理员，我希望界面默认是英文，从而不懂中文的同事也能用。
7. 作为管理员，我希望能一键切换中文，并且下次打开时仍是我选的语言，从而用自己熟悉的语言操作。
8. 作为管理员，我希望在界面上一眼看到 WhatsApp 是已连接、断线重连中还是已登出，从而知道机器人此刻是否在工作。
9. 作为管理员，我希望首次登录时在网页上看到清晰的二维码，从而用手机的"关联设备"直接扫码，不用对着终端里的字符画扫。
10. 作为管理员，我希望二维码过期刷新后，网页上的二维码也自动更新，从而不用手动刷新页面。
11. 作为管理员，我希望能选择"用号码获取配对码"，在页面上填入带国家码的号码后看到 8 位配对码，从而在无法扫码时也能登录。
12. 作为管理员，我希望填过的登录号码被记住（写回 `.env`），从而下次重新关联时不用再填。
13. 作为管理员，我希望号码格式填错时（例如带了 `+` 或空格）页面直接提示，从而不用等 WhatsApp 报一个看不懂的错。
14. 作为管理员，我希望登录成功后页面自动切到"已连接"，从而确认扫码生效。
15. 作为管理员，我希望有"退出并重新关联"按钮，从而在换号码或登录态损坏时不用自己去删数据目录里的文件。
16. 作为管理员，我希望点"退出并重新关联"前界面要求二次确认，并说明机器人会暂时停止回复，从而不会误触断线。
17. 作为管理员，我希望账号在手机端被登出后，界面提示"已登出"并直接给出重新关联的入口，从而不用看终端日志排查。
18. 作为管理员，我希望在表单里修改 `SYSTEM_PROMPT`，并有足够大的多行输入框，从而方便编辑长提示词。
19. 作为管理员，我希望能修改转人工话术，从而调整客户看到的措辞。
20. 作为管理员，我希望能增删转人工关键词，从而按客户实际的说法调整触发条件。
21. 作为管理员，我希望能修改转人工期时长（小时）、会话历史条数、是否回复群聊，从而调整机器人的行为。
22. 作为管理员，我希望能修改模型地址、模型名和超时时间，从而换用别的 OpenAI 兼容服务。
23. 作为管理员，我希望 API Key 只显示掩码、输入框留空表示不改，从而密钥不会在屏幕上泄露，也不会被误清空。
24. 作为管理员，我希望保存后配置立即生效、不用重启，从而改完话术马上就能看到效果。
25. 作为管理员，我希望保存的配置写回 `.env`，原有的注释和其他行保持不变，从而 `.env` 仍然是唯一的配置来源，手动编辑和界面编辑不会互相打架。
26. 作为管理员，我希望填了非法值（例如时长填成负数或文字）时界面拒绝保存并指出是哪一项，从而不会把机器人弄得静默失灵。
27. 作为管理员，我希望 `SYSTEM_PROMPT` 里缺少 `[[HANDOFF]]` 约定时界面给出警告（不阻止保存），从而不会在不知情的情况下关掉"机器人无法回答"这种转人工。
28. 作为管理员，我希望修改转人工期时长不影响已经在转人工期的会话，从而改配置不会让正在跟进的会话提前被机器人插回来。
29. 作为管理员，我希望含 `£` 等非 ASCII 字符的话术保存后不会乱码，从而英镑价格能正常显示。
30. 作为管理员，我希望看到所有会话的列表，按最后一条消息的时间倒序排列，从而最新的对话排在最前面。
31. 作为管理员，我希望列表里每个会话显示电话号和客户的 WhatsApp 昵称，从而认得出是谁。
32. 作为管理员，我希望列表标出哪些会话在转人工期、还剩多久，从而知道哪些会话需要人工跟进。
33. 作为管理员，我希望列表显示每个会话最后一条消息的摘要和时间，从而不用逐个点开就能了解大致情况。
34. 作为管理员，我希望列表每隔几秒自动刷新，从而新消息和状态变化能及时出现。
35. 作为管理员，我希望点开会话后看到只读的会话历史，客户、机器人、运营三方标注清楚，从而知道每句话是谁说的。
36. 作为管理员，我希望会话历史默认显示最近 200 条，需要时可以"加载更多"往前翻，从而长会话也能快速打开。
37. 作为管理员，我希望非文字消息在历史里显示为类型占位（如 "[voice message]"），从而知道客户发过语音或图片。
38. 作为管理员，我希望转人工话术在会话历史里也能看到，从而知道机器人是在哪一刻转人工的。
39. 作为管理员，我希望打开着的会话在有新消息时自动刷新，从而不用手动刷新页面。
40. 作为管理员，我希望对任意会话点"手动转人工"，让机器人立刻停止接待该会话，从而在机器人答偏时马上止损。
41. 作为客户，我希望管理员手动转人工时自己不会收到任何提示，从而对话体验不被打断。
42. 作为管理员，我希望对已在转人工期的会话再点"手动转人工"会重新计满时长，从而延长人工跟进的时间。
43. 作为管理员，我希望点下"手动转人工"时，即使机器人正在生成回复、正在"输入中"，那条回复也不会发出去，从而不会出现"已经叫它停了它还在说"的情况。
44. 作为管理员，我希望对在转人工期的会话点"恢复接待"，让机器人立刻重新接待，从而不用干等转人工期到期。
45. 作为客户，我希望恢复接待时不会突然收到机器人的消息，从而只在我再发消息时才由机器人回复。
46. 作为管理员，我希望恢复接待后，机器人回复时能看到转人工期间客户和运营说过的话，从而接得上前面的对话。
47. 作为运营，我希望在会话详情里直接输入文字发给客户，从而在电脑前工作时不用拿手机。
48. 作为运营，我希望在界面里发出的消息算作运营接管，开启或重新计满转人工期，从而机器人不会紧接着插话。
49. 作为运营，我希望在界面里发出的消息以运营身份计入会话历史，并且只记一次，从而转人工期结束后机器人知道我说过什么，也不会因为回显出现重复记录。
50. 作为运营，我希望发送失败时界面明确提示、输入框里的内容保留，从而可以重试，不用重打。
51. 作为运营，我希望 WhatsApp 未连接时发送按钮不可用并说明原因，从而不会以为消息已经发出去了。
52. 作为运营，我希望在手机上回复客户的效果和以前一样（运营接管），从而管理界面只是多了一种方式，不改变原有习惯。
53. 作为管理员，我希望会话在转人工期到期后，列表里自动显示为机器人接待中，从而状态和实际一致。
54. 作为管理员，我希望机器人断线重连期间管理界面仍能打开、会话和配置照常查看，从而不会因为连接问题什么都看不到。

## Implementation Decisions

- **进程与启动**：管理界面由现有的传输层入口在建立 WhatsApp 连接的同时启动，与机器人同进程。HTTP 用 Node 自带的 `node:http`，只监听 `127.0.0.1`。端口来自新配置项 `ADMIN_PORT`，默认 3000。启动后在终端打印地址，并调用系统命令打开默认浏览器（Windows 用 `start`，macOS 用 `open`，其余平台用 `xdg-open`），打开失败时忽略。端口被占用时打印提示并跳过管理界面，机器人照常运行。不引入任何新依赖。
- **新模块：管理服务**。只对外暴露一个启动函数，参数包括：端口、`.env` 文件路径、一个**连接适配器**。管理服务的所有业务都通过 JSON API 完成，页面本身是随服务下发的静态原生 HTML/CSS/JS（无构建步骤、无前端框架）。
- **连接适配器**（由传输层实现、注入给管理服务）提供四项能力：
  - 查询当前状态：`connecting` / `open` / `qr` / `loggedOut`，处于 `qr` 时附带二维码原始字符串；
  - 为指定号码申请配对码；
  - 退出并重新关联：退出登录、清除登录态、重新发起连接；
  - 以本号身份给某个会话发一条文字消息，返回消息 id。
  传输层需要把现在分散在连接事件里的状态收拢成可查询的当前值，并把"清除登录态后重新连接"做成可调用的动作。
- **二维码渲染**：在服务端用已安装的 `qrcode-terminal` 自带的 QR 编码器，把二维码字符串生成 SVG 返回给页面，不加新的 QR 库。终端里的二维码照常打印。
- **核心逻辑新增的能力**（在现有核心模块里，与传输无关）：
  - **手动转人工**：对会话开启或重新计满转人工期，时长取当前配置。不发转人工话术，也不写会话历史。
  - **恢复接待**：清除该会话的转人工期。不发任何消息，不写会话历史。
  - **运营发送**：把一条文字消息经传输层发出，记下发送 id（使回显不再被当作运营接管重复处理），以运营身份写入会话历史，然后开启或重新计满转人工期。它和客户消息走同一条按会话串行的队列，保证顺序。发送失败时抛出，不写历史、不开窗口。
  - **会话列表查询**：返回每个会话的 id、最后一条消息的摘要和时间、客户昵称、转人工期到期时间。
  - **会话历史分页查询**：按插入顺序倒序，接受"在某条之前"的游标和条数（默认 200）。
- **竞态修复**：机器人每次对外发言（正常回复和转人工话术）之前，都重新检查该会话是否已进入转人工期。如果已进入，丢弃这条回复（不发送、不写会话历史），并收掉"正在输入"。这样，排队外发生的手动转人工，以及 LLM 生成期间发生的状态变化，都能拦住机器人。转人工流程自己发出的话术不受影响：话术发送在开窗口之前。
- **Schema 变更**：新增一张表记录会话的客户昵称（会话 id 为主键，保存最近一次看到的昵称）。昵称只在客户消息里取（不取运营发出的消息），由归一化步骤从 Baileys 消息的 `pushName` 带出，核心逻辑收到客户消息时顺手更新。现有表结构不变；恢复接待时直接删除该会话在 `pause` 表中的记录。
- **配置读写**：
  - 界面可编辑的配置项：`SYSTEM_PROMPT`、`HANDOFF_TEXT`、`PAUSE_KEYWORD`、`PAUSE_HOURS`、`HISTORY_TURNS`、`REPLY_GROUPS`、`OPENAI_BASE_URL`、`OPENAI_API_KEY`、`OPENAI_MODEL`、`LLM_TIMEOUT_MS`。`WHATSAPP_PHONE` 只在登录页写回。`DATA_DIR`、`ADMIN_PORT`、`DEBUG` 不在界面上暴露。
  - 读取时 API Key 只返回是否已设置和掩码形式，不返回明文。保存时 Key 留空表示保持不变。
  - 保存时先整体校验（数值项必须是正数、布尔项必须是 true/false、URL 必须是 http(s)），任何一项不合法就整体拒绝，并返回出错的字段名。
  - 写回 `.env`：按行定位 `KEY=`，只替换值；找不到就追加到文件末尾。其余行和注释原样保留，文件以 UTF-8 读写。值含换行时，按 Node `--env-file` 支持的双引号多行语法写入。`.env` 不存在时就新建。
  - 写回成功后更新内存中的 `CFG`，使配置立即生效。转人工关键词的拆分规则、数值兜底规则和启动时读取 `.env` 的解析规则保持一致。已有的转人工期不受影响，因为 `pause` 表存的是绝对的到期时刻。
  - `SYSTEM_PROMPT` 中不含 `[[HANDOFF]]` 时，保存照常成功，响应里附带警告，由页面展示。
- **HTTP API 约定**（全部是 JSON，路径以 `/api/` 开头；其余路径返回静态页面）：
  - 读取连接状态和二维码（SVG）；申请配对码（请求体是号码，只允许数字，同时写回 `WHATSAPP_PHONE`）；退出并重新关联。
  - 读取配置；保存配置。
  - 会话列表；某会话的历史（带分页游标）。
  - 手动转人工；恢复接待；运营发送（请求体是文字，空白内容拒绝）。
  - 出错时返回非 2xx 状态码，响应体是 `{ error, field? }`。WhatsApp 未连接时，发送、申请配对码等依赖连接的操作返回明确的错误。
- **前端**：
  - 原生单页，每 3 秒轮询会话列表和连接状态；打开会话详情时，同时轮询该会话的历史。
  - 界面文案走一张 en/zh 字典，所选语言记在浏览器本地存储里（读写都要容错），默认英文。
  - 危险操作（退出并重新关联）用页面内的确认对话框，不用浏览器原生的 `confirm`。
  - 转人工期剩余时长由页面根据到期时间和当前时间计算显示。
- **不改变的行为**：WhatsApp 里的运营接管、客户要求、机器人无法回答这三种转人工照旧；终端日志和终端二维码照旧；模拟器照旧。

## Testing Decisions

- **什么是好测试**：只测外部可观察的行为，也就是 HTTP 响应、发给客户的消息、会话历史的内容、转人工期的状态、`.env` 文件的内容，以及之后客户消息的走向。不断言内部函数的调用、SQL 语句或模块内部结构。
- **唯一新增的测试接缝：管理 HTTP JSON API**。测试里在随机端口启动管理服务，注入一个假连接适配器（记录发出的消息和申请过的配对码，状态可由测试切换）和一个临时的 `.env` 文件，用 `fetch` 调用真实的 HTTP 接口。和现有的 e2e 一样，用本地假 LLM 驱动客户消息，并在同一个测试里观察管理操作与消息处理之间的交互。覆盖：
  - 会话列表：昵称、最后一条消息、转人工期到期时间；历史的分页和三方角色。
  - 手动转人工：之后的客户消息只记录不回复，客户没收到任何消息；再点一次会重新计满。
  - 恢复接待：没有给客户发任何消息；之后的客户消息由机器人回复，且模型能看到转人工期间的会话历史。
  - 竞态：让假 LLM 挂起，此时手动转人工，再放行 LLM。机器人的回复不发出、不写入历史。
  - 运营发送：消息经适配器发出；以运营身份写入历史，并且只写一次（模拟回显到达后不重复记录）；开启转人工期；适配器失败时返回错误，不写历史、不开窗口；空白内容被拒绝。
  - 配置保存：`.env` 中对应行被改，注释和无关行保留，缺少的 key 被追加，多行和 `£` 能正确往返；`CFG` 立即生效（之后调用 LLM 用的是新的 `SYSTEM_PROMPT`）；API Key 留空时不改；非法值整体拒绝并返回字段名；缺少 `[[HANDOFF]]` 时返回警告；修改 `PAUSE_HOURS` 后，已在转人工期的会话到期时间不变。
  - 连接：各状态透传正确；处于 `qr` 状态时返回合法的 SVG；配对码请求经过适配器，并写回 `WHATSAPP_PHONE`；非法号码被拒绝；重新关联经过适配器；未连接时发送被拒绝。
  - 安全：服务只监听 `127.0.0.1`（断言绑定地址）。
- **归一化测试**：在现有的归一化单测里加断言，确认客户消息能带出 `pushName`，运营消息不带。
- **Prior art**：现有的离线 e2e 已经示范了"本地假 LLM + 独立数据目录 + 直接调用 `handleIncoming` 并断言历史和转人工期"的写法。新测试照这个写法，数据目录单独放在 `data/` 下以免互相干扰，测试框架继续用 `node --test`。
- **不自动化测试的部分**（在 issue 里列成人工验收步骤）：浏览器页面本身（布局、中英切换、轮询刷新、确认对话框）、自动打开浏览器，以及真实的 Baileys 登录、配对码和重新关联流程。

## Out of Scope

- 局域网、手机或公网访问，以及任何登录鉴权（见 ADR 0002 的后果部分）。
- 多运营协作：分配会话、多坐席、谁在跟进哪个会话。需要时单独评估 Evolution API + Chatwoot 一类方案，另立 ADR。
- 在界面里发送图片、文件、语音、贴纸，或者引用回复、撤回、编辑消息。
- 未读标记、角标、浏览器通知、声音提醒。
- SSE 或 WebSocket 实时推送（先用轮询，慢了再换）。
- 给会话加备注名、标签，或搜索会话历史。
- 在界面上编辑或删除会话历史，导出历史。
- 在界面上修改 `DATA_DIR`、`ADMIN_PORT`、`DEBUG`。
- 桌面应用打包（Electron / Tauri）。
- 模拟器接入管理界面。

## Further Notes

- 在界面里回复客户最初不在范围内（和 WhatsApp 本身重复），后来加了进来：管理员在电脑前办公时不想拿手机。调研过 Evolution API + Chatwoot、WaSphere、OpenWA、WA-AKG 等开源项目，它们都是完整的 WhatsApp 网关，要接管传输层，大多依赖 Docker、Postgres 或 Redis，与 ADR 0001 冲突，所以没有复用。
- 管理界面的回复经传输层发出，其回显通常以 `append` 类型到达，不经过消息处理；万一以 `notify` 到达，也会被发送 id 认出来。所以运营发送必须由核心逻辑自己写入历史、开启转人工期，不能依赖回显。
- 转人工期存的是绝对到期时刻，所以"修改时长不影响已有窗口"不需要额外处理。
- 建议的实现顺序：竞态修复与核心新能力（手动转人工、恢复接待、运营发送、查询）→ 管理服务骨架与会话 API → 配置读写 → 连接适配器与登录 → 前端页面与国际化。
