# Spec: 转人工模型补全

Status: ready-for-agent

术语以根目录 `CONTEXT.md` 为准（客户、运营、机器人、会话、会话历史、非文字消息、转人工、客户要求、机器人无法回答、运营接管、转人工话术、转人工期）。

## Problem Statement

我们承诺“机器人先答，答不上来就交给人”，但现在只有客户说出关键词才会真正转人工，其余情况都会出问题：

- 模型回复“我帮您转人工”后，机器人照样继续自动回复，客户以为有人在跟进，其实没有人。
- 模型调用失败时，客户收不到任何回复，会话也没有转给运营，客户就被晾着。
- 客户发来语音、图片或文件时，机器人既不回复也不记录，客户的问题就这么消失了。
- 运营在手机上亲自回复客户后，机器人不知道运营已经接手，下一条消息还会继续自动回复，两边同时在回复同一位客户。
- 运营说过的话不进会话历史。转人工期结束后，机器人看不到运营回复过什么，可能重复回答，也可能和运营的承诺冲突。
- 转人工话术本身也不进会话历史，机器人不知道自己转过人工。
- 客户在转人工期内再次要求人工，窗口不会重新计时，快到期时机器人会插回来接待。

## Solution

把转人工的三种来源都接通：客户要求、机器人无法回答、运营接管。会话历史要完整记录客户、机器人、运营三方的发言（包括非文字消息和转人工话术），并标明说话方。转人工期内每发生一次新的转人工，窗口都从当时起重新计满。

从客户的角度看：机器人答不了的时候，客户能明确收到转人工话术，之后由运营接待，不会被晾着，也不会同时收到机器人和运营两边的回复。
从运营的角度看：直接在 WhatsApp 里回复客户就等于接手，不需要额外操作。转人工期结束后，机器人能看到运营说过的话，接着往下聊。

## User Stories

1. 作为客户，我希望在说“人工”之后收到转人工话术，从而知道已经有人在跟进。
2. 作为客户，我希望在机器人答不上我的问题时收到转人工话术，而不是一段敷衍或编造的回答，从而得到真实的帮助。
3. 作为客户，我希望在机器人答上一部分、另一部分答不上时，先拿到已答上的内容，再收到转人工话术，从而不必重新提问已答上的部分。
4. 作为客户，我希望在模型服务出错或超时时收到转人工话术，而不是没有任何回应，从而不被晾着。
5. 作为客户，我希望发来的语音能被转给运营处理，从而不必改成打字。
6. 作为客户，我希望发来的无说明图片或文件能被转给运营处理，从而不会让我的问题石沉大海。
7. 作为客户，我希望发出的带说明文字的图片仍由机器人按文字来回复，从而得到即时的回答。
8. 作为客户，我希望回一个贴纸或点一个表情回应时，机器人不会因此转人工，也不会回复我，从而不会被误打扰或误转接。
9. 作为客户，我希望在转人工期内再次要求人工时，窗口能重新计时，从而在等待运营期间机器人不会突然插回来。
10. 作为客户，我希望在转人工期内发的消息都被记下来，从而运营和之后的机器人都能看到。
11. 作为客户，我希望在转人工期内不会收到机器人的自动回复，从而不会同时和机器人、运营两边对话。
12. 作为客户，我希望转人工期结束后机器人回复时知道运营已经答过什么，从而不会得到重复或矛盾的答复。
13. 作为运营，我希望在客户会话里亲自发一句话，就算接手了这个会话，从而不需要记任何指令。
14. 作为运营，我希望我发的图片、语音、文件同样算接手，从而发资料也能让机器人让开。
15. 作为运营，我希望每次我在会话里发言，转人工期都重新计满，从而跟进期间机器人不会插进来。
16. 作为运营，我希望在机器人接待期间主动插话时，机器人立即停止自动回复这个会话，从而避免两边同时回复客户。
17. 作为运营，我希望我说过的话以“运营”的身份记进会话历史，从而之后能区分哪些是我说的、哪些是机器人说的。
18. 作为运营，我希望机器人自己发出的消息不会被当成我在接手，从而机器人正常回复时不会误触发转人工。
19. 作为运营，我希望转人工话术也记进会话历史，从而回看时知道这个会话是从什么时候转给人工的。
20. 作为运营，我希望模型服务大面积故障时，所有受影响的会话都转到人工，从而我能兜住客户，不至于有人被晾着。
21. 作为运营，我希望从 Baileys 直连和 WAHA 两种传输方式上看到的行为一致，从而换传输方式时不需要重新学习。
22. 作为维护者，我希望机器人无法回答由模型输出里的约定标记来表达，而不是去猜模型原文里有没有“转人工”几个字，从而判断稳定、不会误判。
23. 作为维护者，我希望标记在发给客户之前被去掉，从而客户看不到内部标记。
24. 作为维护者，我希望默认 `SYSTEM_PROMPT` 告诉模型答不上来时输出这个标记，从而开箱就能用。
25. 作为维护者，我希望会话历史发给模型时，运营的发言映射为 `assistant`，从而兼容所有 OpenAI 兼容接口。
26. 作为维护者，我希望非文字消息在会话历史里以类型占位的形式记录（例如“[语音]”），从而模型知道那里有一条它看不到内容的消息。
27. 作为维护者，我希望现有的去重和同一会话串行处理的保证不受影响，从而不会因为新增 `fromMe` 消息而出现重复处理或乱序。
28. 作为维护者，我希望所有新行为都能通过现有的离线 e2e 测试验证，从而不需要真机也能回归。

## Implementation Decisions

- **唯一的测试接缝是 `handleIncoming(msg, io)`。** 新行为全部落在与传输方式无关的核心逻辑里，两个传输层只负责把原始消息归一化，自身不带判断逻辑。
- **消息结构扩展：**
  - 新增非文字类型字段，取值为语音、图片、视频、文件等；文字消息不带这个字段。
  - 有说明文字的图片或视频仍然按文字消息处理，行为和现在一样。
  - `fromMe` 的消息不再由传输层或 `shouldReply` 过滤，全部交给核心逻辑处理。
  - 贴纸和表情回应由传输层直接丢弃，不进入核心逻辑。
  - 状态广播，以及未开启群聊时的群消息，仍然照现有规则过滤。
- **分辨机器人回显和运营发言：** `io.send` 要返回所发消息的 id。核心逻辑记住自己发过的 id，`fromMe` 消息如果 id 在其中，就当作机器人回显忽略，其余 `fromMe` 消息都算运营发言。这份记录和去重记录用同一种持久化方式，这样进程重启后，迟到的回显也不会被误判为运营发言。
- **运营发言的处理：** 以“运营”身份存入会话历史（非文字内容同样用类型占位），然后开启转人工期或把它重新计满。不回复，也不触发模型调用。
- **会话历史里的角色：** 从现有的 `user`、`assistant` 两种扩展为客户、机器人、运营三种。发给模型时，客户映射为 `user`，机器人和运营都映射为 `assistant`。存量数据里的 `user` 和 `assistant` 分别就是客户和机器人，不需要迁移。
- **客户消息的处理顺序：**
  1. 去重。
  2. 如果会话处于转人工期内：记录这条消息。如果它命中了转人工关键词，就把窗口重新计满，但不再发转人工话术（客户已经收到过一次）。然后结束处理。
  3. 客户要求（命中关键词）：记录消息，发转人工话术，开启转人工期。
  4. 非文字消息：以类型占位记录，发转人工话术，开启转人工期（归为机器人无法回答）。
  5. 其他情况调用模型。
     - 回复里带约定标记：去掉标记。如果剩下的正文不为空，就按拟人延迟先发正文，并以机器人身份存入历史。然后发转人工话术，开启转人工期。
     - 回复里不带标记：照现在的方式回复。
     - 模型调用失败（报错、超时、返回空内容）：发转人工话术，开启转人工期（归为机器人无法回答）。
- **转人工话术**每次发出后，都以机器人身份存入会话历史。它的 id 同样记入“已发送”，防止回显被误判为运营接管。
- **仍然先发话术、再开启窗口：** 话术发送失败时不开启窗口，这样客户的下一条消息还有机会被回复。这个既有做法保持不变。
- **约定标记**是一个固定字符串，只有代码和默认 `SYSTEM_PROMPT` 知道它。默认 `SYSTEM_PROMPT` 要改成指示模型在答不上来时附上这个标记，不再让模型自己说“转人工”。标记不做成可配置项。
- **转人工期**的时长仍然用现有配置。每次转人工都把到期时间设为“当前时刻 + 时长”，所以如果把窗口重新计满后，新的到期时间比原来更早，也照样覆盖。
- **传输层职责：**
  - Baileys：从原始消息里识别语音、图片、视频、文档，丢掉贴纸和表情回应，`fromMe` 消息照常上交给核心逻辑。发送后返回消息 id。
  - WAHA：订阅能收到自己所发消息的事件，按载荷里的媒体信息识别非文字类型。发送后返回响应里的消息 id。

## Testing Decisions

- 好的测试只看外部行为：给 `handleIncoming` 喂一条消息，然后断言假 `io` 发出了什么、会话历史里记了什么（角色和内容）、转人工期处于什么状态。不断言内部函数或 SQL。
- 主要测试写在离线 e2e 里，沿用现有模式：假 LLM HTTP 服务、假 `io`、独立的数据目录。假 LLM 新增一个“回复带约定标记”的模式（包括“有正文加标记”和“只有标记”两种），现有的 fail 和 hang 模式用来覆盖“模型调用失败即转人工”。假 `io.send` 要返回递增的消息 id，方便测试回显识别。
- 每一条用户故事里可以离线观察的行为，至少有一条 e2e 断言覆盖，重点是以下几项：
  - 机器人无法回答时，先发正文、再发话术，并开启转人工期。
  - 模型调用失败即转人工。
  - 非文字消息先占位记录再转人工。
  - 运营发言开启或重新计满转人工期，并以运营身份存入历史。
  - 机器人回显不触发接管。
  - 转人工期内客户再次要求人工会重新计时。
  - 转人工话术存入历史。
  - 发给模型的历史里，运营发言映射为 `assistant`。
- 纯函数部分（比如标记识别、角色映射）如果单独拆出来，就在现有的 `selftest` 里补断言。
- WAHA 侧的归一化（非文字类型识别、`fromMe` 上交、返回 id）由现有 WAHA e2e 覆盖。Baileys 侧没有离线测试，需要真机验证，并在交付说明里列出验证步骤。
- 现有 e2e 里“转人工暂停”等断言，要按新的顺序和语义更新，不能直接删掉。

## Out of Scope

- 转人工期到期而运营始终没有回复时，给运营提醒或告警（已知限制，先不做）。
- 运营用指令提前结束转人工期（转人工期只按时间到期）。
- 群聊会话历史里区分是哪位客户在说话（群聊默认关闭，等真正启用时再考虑）。
- 识别语音、图片的内容（比如语音转文字、看图作答）。
- 模型服务大面积故障时的限流或熔断，以及避免大量会话同时转人工。
- 转人工期时长按来源区分。

## Further Notes

- 以下三点需要在实现时查证，结果写进代码注释或交付说明：
  - Baileys 里运营从手机或其他已关联设备发出的消息，以什么事件类型到达（现在只处理 `notify`）。
  - WAHA 发送接口返回的消息 id，是否和回显事件里的 id 格式一致。
  - WAHA 回显事件的名称和订阅方式。
- 如果某个传输层拿不到可靠的发送 id，需要另想办法分辨回显（比如按会话加内容做短时匹配）。先停下来找维护者确认，不要自己拍板。
- `PROJECT.md` 里“答不上来或客户要求人工时暂停”的描述，实现后就和代码一致了；README 里有关转人工的运营说明要一起更新，写明“运营直接回复即接管”。
- 大面积故障时所有会话都会进入转人工，这是接受了的取舍：客户被晾着比运营负担重更糟。
